# 검색 필터 개선 계획

작성일: 2026-11-02 (Asia/Seoul)
상태: 계획만 작성. 검색 필터의 제품 동작은 아직 수정하지 않음.
출발점: `Feat/bill-widget`의 검색 필터 점검 결과 및 진단 테스트.

## 작업 경계와 브랜치 순서

1. 현재 브랜치에서는 위젯·탭바·디자인 변경을 정리한다. 색상은 앱 아이콘과 맞춘 따뜻한 흰색·차콜 회색 테마로 확정했다.
2. develop 대상 PR #30에 위젯·탭바·색상·검증 변경을 정리한다.
3. 위젯의 부분 실패·오늘 건수·날짜·미조회 표시·갱신 시각·딥링크 오류를 현재 PR에서 수정했다. 전체 119개 테스트가 예상 실패 없이 통과했다. 실제 위젯 배치와 API 1,000건 한계 등 검증 범위는 [검증 기록](../reviews/2026-11-02-widget-and-ui-validation.md)에 명시한다.
4. PR 검사·리뷰 후 develop에 머지한다.
5. 최신 develop에서 별도 `codex/search-filter-improvements` 브랜치를 만든 뒤 아래 계획을 구현한다. 현재 미커밋 변경이 남은 상태에서 브랜치를 전환하지 않는다.

이 문서는 다음 브랜치의 구현 계획이다. 현재 PR의 수정·리뷰와 별개로 검색 필터 구현과 브랜치 전환은 아직 진행하지 않았다.

PR 포함 여부를 별도로 검토할 파일:
- 제품 UI 변경과 실행 가능한 검증 테스트.
- 앱 아이콘 변경은 다른 작업에서 만든 변경이므로 범위와 최종 파일을 확인한다.
- Xcode 사용자 설정, tmp, 디자인 PDF, 시뮬레이터 녹화/캡처 등은 제품 소스와 함께 무조건 커밋하지 않는다.
- 진단 테스트의 통과는 해당 버그가 수정됐다는 뜻이 아니다. 원하는 정상 동작을 테스트하는 회귀 검증과 구분해서 설명한다.

## 목표

- 조건을 바꾸거나 검색어를 지웠을 때 이전 요청의 응답이 새 화면을 덮어쓰지 않는다.
- 필터 적용 후 빈 페이지 때문에 뒤쪽의 일치 법안을 놓치지 않는다.
- 초기화가 모든 필터를 일관되게 지운다.
- 상태·소관 위원회·기간·즐겨찾기·정렬을 한 화면에서 확인하고 편집한다.
- 현재 확정되는 앱 테마와 라이트/다크 모드를 그대로 사용한다.

## 확인된 문제

| 항목 | 원인 | 검증 상태 |
| --- | --- | --- |
| 초기화 후 소관 위원회가 남음 | 초기화 handler에 committee 제거가 없음 | 코드 확인 |
| 검색 중 필터 변경이 무시됨 | isLoading guard로 새 요청을 버림 | 진단 테스트 재현 |
| 검색어 삭제 후 결과가 다시 뜸 | 이전 요청 취소/응답 구분이 없음 | 진단 테스트 재현 |
| 첫 페이지가 필터 후 0개면 검색 종료 | 표시 개수로 원본 페이지 종료 판단 | 실제 API client→Repository→ViewModel fixture 재현 |
| 조건 편집이 불편함 | 분류 없는 14개 action, 선택 표시와 일괄 적용이 없음 | 메뉴 구성 테스트 확인, 시각 검증 미완료 |

## 1. 검색 요청과 응답의 수명 관리

담당: SearchViewModel.

- 새 검색, 필터 적용, 검색어 삭제마다 요청 세대를 갱신한다.
- 검색 시작 당시의 query/filter/page를 값으로 캡처한다.
- 응답은 현재 세대와 일치할 때만 결과·loading·page·오류 상태를 바꾼다.
- 새 조건의 검색은 기존 isLoading 때문에 버리지 않는다.
- 검색어를 지우면 진행 중이던 응답이 돌아와도 idle 상태를 유지한다.
- 요청 취소는 API 계층이 cancellation을 제공하는 범위에서 사용한다. 정확성은 취소 성공 여부가 아니라 응답 세대 검증으로 보장한다.
- 최근 검색어 저장과 pendingSearchCompletion도 이전 요청의 결과에 반응하지 않도록 정리한다.

완료 조건:
- 느린 A 검색 중 B 조건으로 바꾼 뒤 A가 늦게 도착해도 B 화면에 나타나지 않는다.
- A 요청의 늦은 오류/성공이 B의 로딩 상태를 종료하지 않는다.
- 검색어 삭제 후 과거 결과가 복원되지 않는다.

## 2. 원본 페이지와 표시 결과 분리

담당: API client / Repository / SearchViewModel.

- 페이지 결과에 표시할 snapshots와 next-page 여부를 별도로 전달한다.
- API가 제공하는 총건수/원본 개수/페이지 크기를 확인해 다음 페이지 판단 기준을 정한다. 필터 후 항목 개수로 종료를 판단하지 않는다.
- 이름 검색 이외의 조건을 API에 보낼 수 있는지 공식 API 명세를 먼저 확인한다. 지원되지 않는 조건은 클라이언트 후처리로 유지한다.
- 현재까지 불러온 페이지에서 일치 항목이 없더라도 원본 다음 페이지가 있으면 계속 검색할 수 있어야 한다. 비어 있는 화면에서 스크롤 이벤트에만 의존하지 않는다.
- 자동 연속 요청을 사용한다면 취소·중복 요청 방지와 로딩 상태를 명확하게 관리한다. 임의의 페이지 제한을 전체 검색 완료로 표현하지 않는다.
- 오래된순은 이미 로드한 부분을 뒤집는 것과 전체 검색을 오래된순으로 가져오는 것을 구분한다. 서버 정렬 지원 여부에 맞춰 동작과 문구를 결정한다.
- 결과 수는 API 전체 일치 건수를 모르는 한 ‘현재 표시/불러온 건수’로 표현한다.

완료 조건:
- 첫 페이지 0개·두 번째 페이지 1개 fixture에서 일치 항목을 찾는다.
- 연속으로 비어 있는 페이지 뒤의 일치 항목도 찾는다.
- 마지막 페이지, 전체 0건, 네트워크 실패, 재시도, 필터 변경 중 페이지 요청을 검증한다.
- 중복 ID가 누적되지 않고 새 조건 적용 시 페이지가 초기화된다.

## 3. 필터 모델과 초기화 규칙

담당: BillFilter 및 필요 시 별도 편집 상태 모델.

- 초기화 대상: status=nil, committee=nil, favoriteOnly=false, dateRange=.all, sortOrder=.latest.
- 검색어는 유지한다. 검색어 삭제는 검색창의 동작으로 분리한다.
- 적용 전의 편집 값(draft)과 적용된 값(applied)을 구분한다.
- ‘적용’으로만 화면의 검색 조건을 바꾼다. 닫기/취소는 미적용 편집을 버린다.
- 기간은 날짜 단위 경계를 명확히 한다. 현재 recent(days:)의 시각 때문에 시작 날짜의 법안이 제외되지 않는지 검증한다.
- 위원회 입력은 기존 지원 범위에서 시작하되, 명세 또는 신뢰 가능한 데이터에 근거한 선택 목록으로 개선할 수 있는지 검토한다. 존재하지 않는 위원회명을 임의 생성하지 않는다.

## 4. 전용 필터 바텀시트

담당: 별도 SearchFilterViewController + 표시용 View.

섹션:
1. 진행 상태: 전체 / 제안 / 위원회 / 법사위 / 본회의 / 완료.
2. 소관 위원회: 현재 값 표시, 변경, 해제.
3. 기간: 전체 / 최근 30일 / 최근 1년.
4. 즐겨찾기만: 토글.
5. 정렬: 최신순 / 오래된순.

동작:
- 선택 상태를 체크 표시·굵기·배경 명도 차로 표현한다.
- 하단에 ‘초기화’와 ‘적용’을 둔다. 초기화는 draft를 기본값으로 돌리고 적용 전까지 검색 결과를 바꾸지 않는다.
- 처음 열면 적용된 조건을 draft로 복사한다.
- SearchViewController에는 시트 표시와 적용 결과 전달만 남긴다.
- 필터 버튼의 제목은 짧게 유지하고, 적용 조건 개수/요약은 별도 영역으로 표시한다. 긴 요약 때문에 결과 건수가 눌리거나 잘리지 않도록 한다.
- 작은 화면, iPad, 키보드, 큰 글자, VoiceOver, 라이트/다크 모드에서 확인한다.
- 현재 지원 iOS 16.4에서 사용할 수 있는 UIKit sheet 기능을 사용한다.

## 5. 검증과 커밋 단위

권장 커밋 순서:
1. 필터 초기화 규칙 및 요청 세대 관리 + 회귀 테스트.
2. 원본 페이지 메타데이터와 검색 계속하기 동작 + 통합 테스트.
3. 필터 전용 View/Controller, draft 적용·취소 + UI 검증.
4. 짧은 요약/선택 상태/접근성 보완.

기존 진단 테스트 전환:
- `SearchFilterInspectionTests`의 ‘잘못된 동작을 재현하는 assertion’을 정상 동작 기대값으로 바꾸고 이름을 수정한다.
- 14개 action 구성 테스트는 새 시트의 적용/취소/초기화·선택 상태 검증으로 교체한다.
- 취소 또는 초기화와 API 응답이 교차하는 경우를 포함한다.

머지 전 확인:
- 관련 단위·통합 테스트와 앱/위젯 빌드 통과.
- 시뮬레이터에서 실제 필터 조합, 초기화 후 재검색, 페이지 로딩, 뒤로 이동을 확인.
- API 실패를 ‘검색 결과 없음’으로 오해하게 만들지 않는지 확인.
- 새 필터 작업이 기존 위젯·탭바·딥링크 동작을 바꾸지 않는지 확인.

## 확정 색상 — 앱 아이콘과 통일한 회색

2026-11-02 사용자 결정: 초록색 및 강한 흑백 대비안으로 변경하지 않고, 현재 적용된 따뜻한 흰색·차콜 회색 테마를 유지한다.

- 앱·위젯·색상 에셋의 색감과 라이트/다크 대비를 일관되게 유지한다.
- 선택·진행·완료는 명도 차이와 기존 문구·아이콘·굵기로 구분한다.

제품에는 이미 이 회색 테마가 적용되어 있으므로 이번 결정에서는 제품 색상 코드를 추가로 바꾸지 않는다.
